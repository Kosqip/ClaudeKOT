# ClaudeKOT — требования, решения и чек-лист

Живой документ. Обновляется на каждой значимой итерации. Перед началом новой работы —
свериться с чек-листом ниже, чтобы не возвращаться назад и не терять уже принятые решения.

## Главная цель проекта

Личный веб-интерфейс (форк claudecodeui) на собственном VPS, не привязанный к одному
источнику моделей. Диспетчер задач между:
- **Claude Code** — подписка, официальный CLI
- **Codex** — подписка, официальный CLI
- **API-провайдер** (ранее "OpenRouter") — по ключу, с выбором службы (OpenRouter /
  прямой Anthropic API / прямой OpenAI API)

Смысл — **взаимодополнение бэкендов**, а не параллельная "арена" (это редкий,
второстепенный режим). Главное:
1. Экономия подписок — рутинные задачи не тратят дорогой лимит Claude/Codex
2. Эстафета при лимите — автоматическая передача работы на другой бэкенд
3. Оркестрация с разбивкой задач между бэкендами по ролям

Строго отдельно от этого: авторизация/токены/подпроцессы Claude Code и Codex
(`~/.claude`, аналог Codex) — НЕ трогать, НЕ объединять в общий API-слой.

### Находки на старте Части "эстафета"
- Claude Code: недельный лимит выгорает за 3-4 дня у Pro, у Max выгорал к среде → подтвердило приоритет эстафеты
- У Claude/Codex/OpenRouter разные пулы лимитов → ротация реально экономит, не косметика
- Готовые LLM-роутеры советуют простой keyword-классификатор, не LLM (задержка 200-800мс + скрытые токены) → подтвердило решение #13
- Люди уже вручную собирают "Claude — код, Codex — ревью, crontab" → подтверждает востребованность автоматизации этого вручного процесса
- GitHub issue claudecodeui `#1685` (фича-реквест) описал механизм: Claude Code SDK шлёт `rate_limit_event` с полем `utilization` (процент) ДО реального отказа → привело к реализации проактивной эстафеты (решение #9)

### Находки при унификации API-провайдера
- Проверка документации самой обёртки: готовой системы авторизации под десятки провайдеров нет, но уже подключённый провайдер OpenCode сам идёт через гейтвей "OpenCode Zen" — один ключ, доступ к GPT/Claude/Gemini → подтвердило, что "один провайдер — много служб через общий диспетчер" дешевле по коду, чем провайдер на каждую компанию
- NousResearch/Hermes-Agent: у саб-агентов провайдер/модель/лимиты настраиваются персонально на роль → подтвердило решение #11 (роли), подсказка — лимиты тоже привязывать к роли в будущем оркестраторе (Шаг 2)
- Hermes-Agent умеет мигрировать skills/память при смене инструмента → напоминание: при эстафете (передаче истории на другой бэкенд) не терять контекст активных MCP-инструментов исходной сессии — проверить отдельно перед тем как считать эстафету окончательно готовой

### Находки: razzant/claudexor (похожий проект — личный диспетчер Claude/Codex/Cursor/OpenCode)
- Ротация только на типизированных сигналах лимита, никогда на обычных сетевых ошибках, никогда через явный пин пользователя → независимое подтверждение решения #7
- Передают историю при хендоффе через ФАЙЛ на диске (указывают путь в промпте), а не инлайном в сообщении → наш текущий `renderHistoryAsText` инлайнит всю историю прямо в текст — риск раздуть промпт на длинной беседе. **Надо исправить** (см. чек-лист/TODO ниже)
- Старые сообщения сжимаются (кэшированное LLM-резюме, иначе механическое сокращение), не просто дампятся целиком
- Один `AGENTS.md` как источник правды + генерируемый `CLAUDE.md`-мостик для Claude → совпадает с нашим решением по memory.md, ничего менять не нужно
- У делегированных саб-агентов — ограниченный набор инструментов (старт/проверка/чтение, без apply/settings) и ограничение глубины вложенности → важно для будущего Шага 2 (оркестратор): делегирование не должно давать полный доступ бездумно
- Их модель роутинга — Pool + Primary + Routing Goal (auto/quality/economy), богаче нашего простого порядка приоритета → кандидат на обогащение ролей в Шаге 2
