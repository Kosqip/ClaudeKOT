# ClaudeKOT — требования, решения и чек-лист

Живой документ. Обновляется на каждой значимой итерации. Перед началом новой работы —
свериться с чек-листом ниже, чтобы не возвращаться назад и не терять уже принятые решения.

## Главная цель проекта

Личный веб-интерфейс (форк claudecodeui) на собственном VPS, не привязанный к одному
источнику моделей. Диспетчер задач между:
- **Claude Code** — подписка, официальный CLI
- **Codex** — подписка, официальный CLI
- **API-провайдер** (ранее "OpenRouter") — по ключу, с выбором службы (OpenRouter /
  прямой Anthropic API / прямой OpenAI API)

Смысл — **взаимодополнение бэкендов**, а не параллельная "арена" (это редкий,
второстепенный режим). Главное:
1. Экономия подписок — рутинные задачи не тратят дорогой лимит Claude/Codex
2. Эстафета при лимите — автоматическая передача работы на другой бэкенд
3. Оркестрация с разбивкой задач между бэкендами по ролям

Строго отдельно от этого: авторизация/токены/подпроцессы Claude Code и Codex
(`~/.claude`, аналог Codex) — НЕ трогать, НЕ объединять в общий API-слой.

## Исправленные баги (не флуктуации, настоящие дефекты)

Два теста долго считались "преэкзистентной нестабильностью" под нагрузкой — при полной проверке (2026-11-12) оказалось, что оба воспроизводились изолированно и были настоящими багами:

1. **`buildGitCloneEnvironment` наследовал чужие `GIT_CONFIG_*` из окружения.** Функция копировала весь `process.env` целиком — если хост-машина (например эта песочница из-за своего git-прокси) уже экспортирует `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`, они просачивались в клон репозитория, хотя при отсутствии токена credential helper должен оставаться гарантированно пустым. Исправлено — теперь явно вычищаются перед построением окружения клона.
2. **Бинарник `ripgrep` не был установлен** — `npm install --ignore-scripts` (использовали, чтобы не тащить Electron) также пропустил postinstall `@vscode/ripgrep`, который качает `rg`. Из-за этого поиск по истории разговоров реально падал с `ENOENT`, просто ошибка маскировалась под "не в том порядке событий" в тесте. Исправлено локально (скопирован системный `rg`), но **это нужно учесть при настройке реального деплоя** — на VPS `npm install` без `--ignore-scripts` должен скачать `rg` сам; если там тоже используется `--ignore-scripts` или сеть блокирует `api.github.com`, нужно будет так же подложить системный `ripgrep` вручную.

### Полная перепроверка проекта (2026-11-12): что нашлось сверх тестов

До этой проверки приложение ни разу не запускалось целиком — только тесты. Запуск собранного сервера, реальные запросы и просмотр интерфейса в браузере выявили ошибки, которых тесты не видели:

1. **Авто-эстафета для Codex и Custom API была мёртвым кодом.** Оба рантайма сами ловят свои ошибки и отправляют их сообщением `error`, ничего не бросая, а перехват стоял только на брошенном исключении. Теперь проверяется и каждое сообщение `error`.
2. **Лимит Custom API не распознавался.** После унификации провайдера текст ошибки стал `openrouter|anthropic|openai request failed (429)`, а детектор искал старое `OpenRouter request failed`.
3. **Повторные и встречные эстафеты.** Claude сообщает о лимите много раз за ход — каждое сообщение открывало бы новую запасную сессию; два исчерпанных бэкенда перекидывали бы разговор друг другу бесконечно. Теперь: одна эстафета на сессию, исчерпанный бэкенд не выбирается запасным до сброса лимита.
4. **Запасной бэкенд не проверялся на готовность** — выбирался первый по списку, даже если он не установлен или не авторизован.
5. **Проактивная эстафета запускала второго агента посреди хода первого** — оба работали бы над одной задачей в одной папке. Теперь при достижении порога перенос откладывается до конца текущего ответа, и запасная сессия получает контекст в режиме ожидания, а не «продолжай»; немедленно и с продолжением работы переносится только сессия, которой Claude реально отказал.
6. **Эстафета была невидимой** (только запись в серверном логе) — вопреки решению #8. Теперь в исходной сессии показывается баннер со ссылкой на новую.
7. **Порядок запасных бэкендов из настроек не применялся** для Codex/Custom API (читался только в ветке Claude).
8. **Кнопки микса, роутера, оркестратора и ручной эстафеты «висели»**, пока агент не закончит весь ход: HTTP-запрос ждал завершения. Теперь запрос возвращается, как только ходы запущены.
9. **Сессии Custom API открывались пустыми**: провайдер не регистрировал свой идентификатор, и приложение считало, что переписки нет. Ошибки и вопрос при отсутствии ключа тоже не сохранялись.
10. **Ошибка посреди потока ответа** (перегрузка сервиса) терялась молча — пустой ответ без объяснения.
11. **Роутер выдавал «сложное решение, определено автоматически»**, когда на самом деле не нашёл ни одного ключевого слова.
12. **Панели под чатом занимали пол-экрана**, показывали UUID вместо названий сессий, были только на английском; список сессий в миксе брался из устаревшей копии проекта (пустой при открытии по прямой ссылке). Теперь это одна строка кнопок, раскрывающих нужную панель, с переводом на русский и собственной загрузкой списка сессий.
13. Обёртка над writer теряла методы, которых нет в базовом типе (`updateWebSocket`, `getSessionId`) — заменена на Proxy.

Добавлены тесты, которых не было: первый набор для рантайма Custom API (7), перехват сигналов лимита и неблокирующий запуск (4), эстафета целиком на настоящей базе (5).

**Не проверено вживую — нет ключей/подписок в среде разработки:** реальный ответ OpenRouter/Anthropic/OpenAI, реальное событие лимита от Claude, JSON-план от модели-оркестратора, чтение файла с историей запасным CLI. Идентификаторы моделей OpenRouter и OpenAI в каталоге по умолчанию не сверены с их актуальными каталогами — при ошибке «модель не найдена» добавить свою модель в библиотеке моделей.

### Находки при унификации API-провайдера
- Проверка документации самой обёртки: готовой системы авторизации под десятки провайдеров нет, но уже подключённый провайдер OpenCode сам идёт через гейтвей "OpenCode Zen" — один ключ, доступ к GPT/Claude/Gemini → подтвердило, что "один провайдер — много служб через общий диспетчер" дешевле по коду, чем провайдер на каждую компанию
- NousResearch/Hermes-Agent: у саб-агентов провайдер/модель/лимиты настраиваются персонально на роль → подтвердило решение #11 (роли), подсказка — лимиты тоже привязывать к роли в будущем оркестраторе (Шаг 2)
- Hermes-Agent умеет мигрировать skills/память при смене инструмента → напоминание: при эстафете (передаче истории на другой бэкенд) не терять контекст активных MCP-инструментов исходной сессии — проверить отдельно перед тем как считать эстафету окончательно готовой

### Находки: razzant/claudexor (похожий проект — личный диспетчер Claude/Codex/Cursor/OpenCode)
- Ротация только на типизированных сигналах лимита, никогда на обычных сетевых ошибках, никогда через явный пин пользователя → независимое подтверждение решения #7
- Передают историю при хендоффе через ФАЙЛ на диске (указывают путь в промпте), а не инлайном в сообщении → наш текущий `renderHistoryAsText` инлайнит всю историю прямо в текст — риск раздуть промпт на длинной беседе. **Надо исправить** (см. чек-лист/TODO ниже)
- Старые сообщения сжимаются (кэшированное LLM-резюме, иначе механическое сокращение), не просто дампятся целиком
- Один `AGENTS.md` как источник правды + генерируемый `CLAUDE.md`-мостик для Claude → совпадает с нашим решением по memory.md, ничего менять не нужно
- У делегированных саб-агентов — ограниченный набор инструментов (старт/проверка/чтение, без apply/settings) и ограничение глубины вложенности → важно для будущего Шага 2 (оркестратор): делегирование не должно давать полный доступ бездумно

### Цикл поиска перед Частью 3 (роутер) — 2026-11-12

**musistudio/claude-code-router (CCR)** — самый близкий аналог нашего будущего роутера:
- Встроенные task-type ключи: `default`/`background`/`think`/`longContext`/`webSearch`/`image` — ось "форма задачи" (контекст большой/маленький, нужен поиск, картинка), ОТЛИЧАЕТСЯ от нашей оси из ТЗ ("рутина/кодинг/второе мнение/сложное решение" — это ось "тип работы", не форма). Не конкурирует с нашими тегами, скорее дополняет на будущее — см. п.15 ниже
- Правила матчатся по условиям на заголовках/теле запроса, есть префиксы, rewrite, retries, упорядоченный fallback моделей, credential pools/key rotation
- Хранилище правил мигрировало с `config.json` на SQLite — намёк, что плоский JSON-конфиг на практике становится неудобным при росте правил; нам пока рано, но держать в уме если правил станет много
- Известная грабля у них: Windows-сборка ломается на native-модуле `better-sqlite3` под Electron — ровно та же категория проблемы, с которой мы сами столкнулись при установке (пересборка нативного модуля)

**Другие похожие проекты (беглый обзор, для общего контекста, не для копирования):**
- CLI-JAW, claw-orchestrator, agent-dispatch (Rust, durable task queue), SuperAICore — все решают близкую задачу "один вход, несколько CLI-бэкендов", но без браузерного UI (та же проблема, что у Claudexor)
- Общий паттерн из этих находок: health-aware pool (брать живой бэкенд, не мёртвый) + явный, аудируемый список "кому можно передать задачу" (handoffs array) — у нас это уже есть через `providerRoles`/`hasRuntime`, просто неявно

**Общие практики мультиагентного роутинга (обзорные источники, не конкретный код):**
- Три семейства: rule-based / supervised ML / LLM-based — подтверждает решение #13 (мы выбрали rule-based)
- Рекомендуемый гибрид: дешёвый keyword/rule-проход первым, LLM — только для действительно неоднозначных случаев (это НЕ то же самое, что "LLM-классификатор перед каждым роутингом", который мы отвергли — тут LLM это fallback для погранслучаев, а не основной путь). Кандидат на будущее улучшение Части 3, не обязателен для MVP
- Явный аудируемый список "куда агент может передать задачу" — подтверждает решение #11/#12 (роли + настраиваемый порядок уже аудируемы и явны)

| Аудируемый явный список ролей/приоритета | Уже есть (`providerRoles`, `handoffFallbackOrder`) | Ничего не делать, уже соответствует практике |
| Гибрид keyword+LLM-fallback для неоднозначных случаев | Не реализовано | Не делать в MVP Части 3 — ТЗ прямо просило простые правила без LLM; зафиксировать как возможное будущее улучшение, не блокирует MVP |
| SQLite вместо JSON для правил роутинга при их росте | Не применимо сейчас | У нас в Части 3 будет мало правил (4 тега) — простой конфиг-файл достаточен; пересмотреть только если правил станет десятки |
